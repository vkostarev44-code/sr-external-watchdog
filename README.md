# Внешний сторож сайта

Проверяет https://steelracing.ru/ (HTTP 200 и признак магазина в HTML) и https://lk.steelracing.ru/login (HTTP 200 и форму входа) каждые 15 минут, на минутах 13/28/43/58. Неудачная проверка повторяется до трёх раз с паузой 45 секунд и таймаутом 20 секунд на страницу. Одна недоступная цель открывает общую аварию; восстановление — когда доступны обе.

В Telegram приходят только переходы: «🔴 Внешний сторож: сайт недоступен…» и «🟢 …снова доступен, простой ~N мин». Время приблизительное, с первой неудачной проверки; между проверками сбой мог начаться раньше. Повторов каждые 15 минут нет. Расписание GitHub не имеет SLA, может задерживаться или пропускать запуски.

Ключи — только Secrets Actions `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`; отправка напрямую, без прокси. Ручной запуск: Actions → «Внешний сторож» → Run workflow, `dry_run=true` проверяет живые страницы без отправок и записи состояния. Дополнительный `mock=true` проверяет переходы без сети. `send_test=true` вместе с `dry_run=false` — одноразовый тест, повтор блокируется навсегда отдельным issue. Обычная работа расписания и реальный тест разрешены только из основной ветки.

Расписание запускает проверки только при Actions Variable `MONITOR_ENABLED=true`. Установите её после успешных живого dry-run, mock и одноразового теста; до этого расписание пропускается, а ручные безопасные проверки доступны. Переключение переменной в `false` останавливает только плановые проверки.

Состояние хранится в одном публичном issue: оно переживает новый runner без ненадёжного cache, доступно стандартному `GITHUB_TOKEN`. Не удаляйте служебные issues и не помещайте туда данные чата. Первый здоровый запуск молчит, первый запуск во время аварии предупреждает. Резерв уведомления сохраняется до отправки: при обрыве сообщение может не прийти, но повтора не будет. Строгая доставка «ровно один раз» при сетевом сбое не гарантируется — нужен ручной контроль. Одновременные запуски сериализованы.

GitHub может отключить расписание после 60 дней неактивности. Монитор ежемесячно обновляет этот маркер автокоммитом, но SLA GitHub и влияние активности бота не гарантируются. Проверяйте вкладку Actions; при отключении нажмите Enable workflow. Отключение: Actions → нужный workflow → Disable workflow. Адреса и маркеры меняются в `TARGETS` через PR.

Если workflow активен и ручные запуски проходят, но события `schedule` отсутствуют, GitHub рекомендует пользователю с правом записи изменить значение `cron`: это может восстановить расписание и обновить связанного actor. Текущие минуты изменены для такой проверки через обычный PR, который сливает пользователь; это не доказанное устранение причины. После слияния нужен именно запуск с `event=schedule`, ручной запуск его не заменяет. [Официальное описание](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows#scheduled-workflow-stopped-running).

Ежемесячный keepalive оставлен без изменения: нет подтверждения, что бот-коммит в основной ветке подавляет будущие независимые события `schedule`. Документированное ограничение `GITHUB_TOKEN` касается событий, вызванных самим токеном, например `push`. Перенос бот-коммита в другую ветку также не даёт документированной гарантии обхода 60-дневного отключения. Механизм активности и его результат нужно контролировать, не считать гарантией работы cron. [Правило токена](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs).
